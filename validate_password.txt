REVERSE-ENGINEERING STUDY NOTES
C-LIKE PSEUDOCODE + DATA FLOW + CONTROL FLOW
======================================================================

Purpose:
    Understand the logic represented by the supplied AArch64
    disassembly.

Important:
    This is PSEUDOCODE, not compilable C.
    Unknown functions are intentionally represented as helper()
    functions because their implementations were not provided.

======================================================================
PART 1 - FUNCTION FUN_ffff000050fa228c
======================================================================

Original high-level observation:

    Input:
        w0 = some field/code identifier
        w1 = value associated with that identifier

    The function first calculates:

        index = w0 - 0x6B

    It then checks whether index is in the range:

        0 .. 5

    If the value is outside that range, execution goes to an
    "unsupported field" error path.

    Otherwise, a byte table is consulted.

        table[index] -> case/offset selector

    The selector is multiplied by 4 and added to a base address,
    producing the destination of an indirect branch.

    In other words, this is essentially a SWITCH statement.

----------------------------------------------------------------------
PSEUDOCODE
----------------------------------------------------------------------

int function_FUN_ffff000050fa228c(int field_id, int value)
{
    /*
     * Convert the incoming field identifier into a zero-based
     * switch index.
     *
     * Example:
     *
     *     field_id = 0x6B  -> index = 0
     *     field_id = 0x6C  -> index = 1
     *     ...
     *     field_id = 0x70  -> index = 5
     */
    int index = field_id - 0x6B;

    /*
     * The assembly performs:
     *
     *     cmp index, #5
     *     b.hi unsupported
     *
     * Therefore only indexes 0 through 5 are accepted.
     *
     * Because this is an unsigned-style "higher than" comparison,
     * negative values also effectively fail the intended range check
     * when represented as the original 32-bit value.
     */
    if (index > 5)
    {
        /*
         * w0 = 0xFFFFFFFF
         *
         * x1 points at:
         *
         * "mot_sec: Unsupported efuse field to get written\n"
         *
         * The helper is called with an error value.
         */
        log_or_report_error(
            -1,
            "mot_sec: Unsupported efuse field to get written\n"
        );

        return -1;
    }

    /*
     * switchdataD_ffff00005101b5e4 is a byte table.
     *
     * table[index] gives a small selector.
     *
     * The assembly then does:
     *
     *     target = switch_base + table[index] * 4
     *
     * and:
     *
     *     br target
     *
     * This is compiler-generated switch dispatch.
     */
    unsigned char selector = switch_table[index];

    /*
     * Conceptually:
     *
     *     switch (index)
     *     {
     *         case 0: goto CASE_0;
     *         case 1: goto CASE_1;
     *         ...
     *         case 5: goto CASE_5;
     *     }
     *
     * We can reconstruct the individual cases from the
     * instructions following the indirect branch.
     */


CASE_0:

    /*
     * The case bodies all follow the same general pattern:
     *
     *     w0 = input value
     *     w1 = some operation parameter
     *     helper(w0, w1)
     *     result is shifted
     *
     * The exact meaning of helper() cannot be established from
     * this function alone.
     */

    /*
     * One possible case:
     *
     *     result = helper(value, 1);
     *     result = result << 14;
     */
    /*
     * This corresponds to:
     *
     *     mov w0,w1
     *     mov w1,#1
     *     bl  FUN_...0da0
     *     lsl w1,w0,#0xe
     */
    goto CASES_RECONSTRUCTED;


CASES_RECONSTRUCTED:

    /*
     * The disassembly contains several case blocks.
     *
     * They perform transformations with different shift amounts.
     *
     * These are the observable operations:
     *
     *     helper(value, 1) << 14
     *     helper(value, 1) << 15
     *     helper(value, 1) << 1
     *     helper(value, 1) << 2
     *     helper(value, 16) << 16
     *
     * One case simply copies the helper result.
     *
     * Because the switch-table byte values themselves were not
     * supplied, we should NOT arbitrarily assign each operation
     * to field IDs 0x6B ... 0x70.
     */

    /*
     * Conceptual representation:
     */

    switch (index)
    {
        case CASE_SELECTOR_A:
        {
            int result = helper_ffff000050fa0da0(value, 1);

            /*
             * The original assembly places the shifted result
             * into w1 and then jumps to the common continuation.
             */
            result = result << 14;

            return common_fuse_write(result);
        }

        case CASE_SELECTOR_B:
        {
            int result = helper_ffff000050fa0da0(value, 1);

            result = result << 15;

            return common_fuse_write(result);
        }

        case CASE_SELECTOR_C:
        {
            int result = helper_ffff000050fa0da0(value, 1);

            result = result << 1;

            return common_fuse_write(result);
        }

        case CASE_SELECTOR_D:
        {
            int result = helper_ffff000050fa0da0(value, 1);

            result = result << 2;

            return common_fuse_write(result);
        }

        case CASE_SELECTOR_E:
        {
            int result = helper_ffff000050fa0da0(value, 16);

            result = result << 16;

            return common_fuse_write(result);
        }

        case CASE_SELECTOR_F:
        {
            int result = helper_ffff000050fa0da0(value, 1);

            /*
             * No additional shift is visible in this case.
             */
            return common_fuse_write(result);
        }
    }
}

int write_field(int field_id, int value)
{
    int index = field_id - 0x6B;

    if (index > 5)
    {
        report_error(
            -1,
            "Unsupported efuse field"
        );

        return -1;
    }

    /*
     * A lookup table determines which transformation is used.
     */
    switch (switch_table[index])
    {
        case OP_SHIFT_14:
            value = helper(value, 1) << 14;
            break;

        case OP_SHIFT_15:
            value = helper(value, 1) << 15;
            break;

        case OP_SHIFT_1:
            value = helper(value, 1) << 1;
            break;

        case OP_SHIFT_2:
            value = helper(value, 1) << 2;
            break;

        case OP_SHIFT_16:
            value = helper(value, 16) << 16;
            break;

        case OP_NONE:
            value = helper(value, 1);
            break;
    }

    /*
     * Common low-level operation.
     *
     * The actual semantics of this helper must be recovered from
     * FUN_ffff000050f63f40 before giving it a more specific name.
     */
    int status = low_level_operation(6);

    if (status != 0)
    {
        report_error(
            -1,
            "Writing MTK Spare C_CTRL0 fuse bank failed: %d",
            status
        );

        return -1;
    }

    return 0;
}

PART 2 - FUN_ffff000050f923f0
======================================================================

This is a very small accessor.

Assembly:

    cbz  x0, return_zero
    ldrh w8,[x0,#2]
    rev  w8,w8
    lsr  w0,w8,#16
    ret

PSEUDOCODE:

uint32_t get_version_or_type(void *object)
{
    /*
     * If the input object is NULL, return zero.
     */
    if (object == NULL)
        return 0;

    /*
     * Read a 16-bit value at offset +2.
     *
     * This suggests that the object has at least this layout:
     *
     *     offset 0 : unknown
     *     offset 2 : 16-bit field
     *     ...
     */
    uint16_t raw16 = *(uint16_t *)((char *)object + 2);

    /*
     * rev operates on the full 32-bit register.
     *
     * The important conceptual effect is that the bytes are
     * reversed before the upper 16 bits are selected.
     */
    uint32_t converted = byte_reverse_32(raw16);

    /*
     * Extract the upper 16 bits.
     */
    uint32_t result = converted >> 16;

    return result;
}


======================================================================
PART 3 - FUN_ffff000050f923cc
======================================================================

This is related to the previous accessor.

Assembly:

    cbz  x0, return_zero
    ldrh w8,[x0,#2]
    lsl  w8,w8,#16
    rev  w8,w8
    cmp  w8,#2
    mov  w8,#42
    csel w0,w9,w8,cc
    ret

The interesting part is:

    ldrh
    lsl #16
    rev
    cmp #2

This is effectively checking the encoded value in the +2 field
against a particular version/type value.

The conditional select is:

    csel w0, w9, w8, cc

where:

    w9 = 0x28 = 40
    w8 = 0x2A = 42

"cc" means carry clear / unsigned lower.

Therefore the function returns one of:

    40
    42

depending on the comparison.

PSEUDOCODE:

int get_datablock_mode(void *object)
{
    /*
     * NULL object -> 0.
     */
    if (object == NULL)
        return 0;

    uint16_t raw16 =
        *(uint16_t *)((char *)object + 2);

    /*
     * Reconstruct the value represented by the encoded field.
     */
    uint32_t value =
        byte_reverse_32((uint32_t)raw16 << 16);

    /*
     * Compare against 2.
     */
    if (value < 2)
    {
        /*
         * cc / carry-clear corresponds to unsigned lower.
         *
         * Return 0x28 = 40.
         */
        return 0x28;
    }
    else
    {
        /*
         * Return 0x2A = 42.
         */
        return 0x2A;
    }
}


======================================================================
PART 4 - MAIN VALIDATION FUNCTION
======================================================================

FUN_ffff000050f9014c

This is the most interesting function for understanding the
validation/verification DATA FLOW.

It appears to perform approximately these stages:

    1. Obtain/read a datablock.
    2. Check whether that operation succeeded.
    3. Extract/interpret the datablock version/type.
    4. Handle version 1.
    5. Handle version 2.
    6. Reject unsupported versions.
    7. Potentially validate a hash/password.
    8. Return a status.

The exact semantics of the helper functions cannot be proven
without their bodies.

----------------------------------------------------------------------
STEP 1 - INITIALIZATION
----------------------------------------------------------------------

The function allocates a 0xA0-byte stack frame.

It stores:

    x19 = original input argument

It also initializes a local pointer to NULL:

    local_object = NULL

And:

    local_size_or_value = 0x20

Then it calls:

    FUN_ffff000050f90010(...)

Conceptually:

    object = NULL;
    size = 0x20;

    result = get_datablock(input, &object, &size);

The exact argument interpretation depends on FUN_ffff000050f90010,
which was not supplied.

----------------------------------------------------------------------
STEP 2 - TEST RESULT OF INITIAL OPERATION
----------------------------------------------------------------------

Assembly:

    tbz w0,#0,...

This tests bit 0 of the return value.

Conceptually:

    if ((result & 1) == 0)
        goto FAILURE_OR_NO_DATA;

So this is NOT necessarily:

    if (result == 0)

It specifically tests bit zero.

This distinction is important.

----------------------------------------------------------------------
STEP 3 - VALIDATE / INTERPRET DATABLOCK
----------------------------------------------------------------------

The function passes:

    &local_object
    &local_size

to:

    FUN_ffff000050f90f78

Conceptually:

    status = process_datablock(
        &object,
        &size
    );

Then:

    if (status != 0xF)
        goto unsupported_or_failure;

This is a very strong indication that 0xF is a specific
expected status/type/result from that helper.

----------------------------------------------------------------------
STEP 4 - CHECK OBJECT POINTER
----------------------------------------------------------------------

The code then performs:

    if (object == NULL)
        goto failure;

Therefore, reaching the validation stage requires both:

    status == 0xF
    object != NULL

----------------------------------------------------------------------
STEP 5 - DETERMINE VERSION
----------------------------------------------------------------------

The object is passed to:

    FUN_ffff000050f923f0

That function reads the field at:

    object + 2

and extracts a value.

Conceptually:

    version = get_version_or_type(object);

Then:

    switch (version)
    {
        ...
    }

The exact values need to be interpreted carefully because the
accessor performs byte manipulation.

----------------------------------------------------------------------
STEP 6 - SECOND INTERPRETATION OF SAME FIELD
----------------------------------------------------------------------

The object is also passed to:

    FUN_ffff000050f923cc

Conceptually:

    mode = get_datablock_mode(object);

Then:

    mode &= 0xFFFF;

The code checks:

    if (mode == 2)
        ...
    else if (mode == 1)
        ...
    else
        ...

Therefore the relevant high-level logic is:

    switch (mode)
    {
        case 2:
            ...
            break;

        case 1:
            ...
            break;

        default:
            ...
            break;
    }


======================================================================
VERSION / MODE 2 PATH
======================================================================

When:

    (mode & 0xFFFF) == 2

the code sets:

    w21 = 1
    w22 = 0x20

and obtains a string:

    "mot_sec: validate_hash_password: Version 2 datablock\n"

This string is passed to the logging/reporting helper.

Conceptually:

    log(
        "Version 2 datablock"
    );

Then:

    helper(...)

is called with:

    w0 = 1

This suggests that the value 1 is a mode/operation selector.

Again, the exact meaning cannot be determined without the
callee's implementation.


======================================================================
VERSION / MODE 1 PATH
======================================================================

When:

    (mode & 0xFFFF) == 1

the code sets:

    w21 = 0
    w22 = 0x14

and obtains:

    "mot_sec: validate_hash_password: Version 1 datablock\n"

Conceptually:

    log(
        "Version 1 datablock"
    );

Then both:

    w21
    w22

are retained for the common validation path.


======================================================================
UNSUPPORTED MODE PATH
======================================================================

If the mode is neither 1 nor 2:

    w21 != 1
    w21 != 2

the code goes to an error path.

It references:

    "mot_sec: validate_hash_password: Unsupported datablock\n"

Conceptually:

    log(
        "validate_hash_password: Unsupported datablock"
    );

The function then returns its failure/status value.


======================================================================
IMPORTANT DATA-FLOW VARIABLE
======================================================================

The register:

    w21

is particularly important.

It is set according to the detected datablock mode.

For mode 2:

    w21 = 1

For mode 1:

    w21 = 0

Later the function returns:

    w20

and w20 was initially zero.

Thus w21 appears to be a parameter controlling the subsequent
validation operation rather than simply the final return code.


======================================================================
RECONSTRUCTED HIGH-LEVEL FUNCTION
======================================================================

int validate_hash_password(void *input)
{
    /*
     * Local state.
     */
    void *datablock = NULL;

    /*
     * Initial/default value supplied to the first helper.
     */
    uint32_t size_or_parameter = 0x20;

    /*
     * Result of obtaining/processing the datablock.
     */
    int result =
        get_datablock(
            input,
            &datablock,
            &size_or_parameter
        );

    /*
     * Assembly uses TBZ on bit 0.
     *
     * Therefore we test the LOW BIT rather than assuming
     * that the entire return value must equal 1.
     */
    if ((result & 1) == 0)
    {
        /*
         * No successful datablock condition.
         */
        return 0;
    }

    /*
     * Further processing of the datablock.
     *
     * Two local variables are supplied by address.
     */
    int processed =
        process_datablock(
            &datablock,
            &size_or_parameter
        );

    /*
     * Only status 0xF continues down the validation path.
     */
    if (processed != 0xF)
    {
        /*
         * Unsupported/error condition.
         */
        return 0;
    }

    /*
     * A successful processing status is not sufficient.
     * The returned datablock pointer must also be non-NULL.
     */
    if (datablock == NULL)
    {
        return 0;
    }

    /*
     * Determine the encoded version/type.
     */
    int version =
        get_version_or_type(datablock);

    /*
     * Determine the validation mode.
     */
    int mode =
        get_datablock_mode(datablock);

    mode &= 0xFFFF;


    /*
     * These variables correspond approximately to w20/w21/w22.
     */
    int return_value = 0;
    int validation_mode;
    int validation_parameter;


    /*
     * MODE 2
     */
    if (mode == 2)
    {
        /*
         * The assembly assigns:
         *
         *     w21 = 1
         *     w22 = 0x20
         *
         * and logs "Version 2 datablock".
         */
        validation_mode = 1;
        validation_parameter = 0x20;

        log(
            "mot_sec: validate_hash_password: "
            "Version 2 datablock\n"
        );
    }

    /*
     * MODE 1
     */
    else if (mode == 1)
    {
        /*
         * The assembly assigns:
         *
         *     w21 = 0
         *     w22 = 0x14
         *
         * and logs "Version 1 datablock".
         */
        validation_mode = 0;
        validation_parameter = 0x14;

        log(
            "mot_sec: validate_hash_password: "
            "Version 1 datablock\n"
        );
    }

    /*
     * UNSUPPORTED
     */
    else
    {
        log(
            "mot_sec: validate_hash_password: "
            "Unsupported datablock\n"
        );

        return 0;
    }


    /*
     * At this point the original function continues into a
     * validation/error-handling sequence.
     *
     * The supplied disassembly shows calls to:
     *
     *     FUN_ffff000050f29978
     *     FUN_ffff000050f9b6f0
     *
     * but does not provide their implementations.
     *
     * Therefore we must NOT invent what cryptographic or password
     * comparison operation they perform.
     */


    /*
     * Conceptual continuation:
     */

    int validation_result =
        validate_using_datablock(
            datablock,
            validation_mode,
            validation_parameter
        );


    /*
     * If the validation helper fails, another error/reporting
     * operation is conditionally invoked.
     */
    if (validation_result == 0)
    {
        return return_value;
    }

    /*
     * Actual return semantics depend on the omitted helper bodies.
     */
    return return_value;
}

======================================================================
PART 6 - HOW THE CODE VALIDATION / VERIFICATION DATA FLOWS
======================================================================

There are several distinct concepts here.

Do NOT collapse them into one operation.

The observed code has at least four stages:

    A. DATA ACQUISITION
    B. DATABLOCK INTERPRETATION
    C. VERSION/MODE SELECTION
    D. VALIDATION

----------------------------------------------------------------------
A. DATA ACQUISITION
----------------------------------------------------------------------

The first helper appears to populate:

    datablock
    parameter/size

The code checks bit 0 of its return value.

Therefore:

    acquisition_success =
        (result & 1) != 0

Only if that condition is true does the code continue.

This is a control-flow gate.


----------------------------------------------------------------------
B. DATABLOCK PROCESSING
----------------------------------------------------------------------

The next helper receives pointers to the local variables:

    &datablock
    &parameter

That means the helper may modify those variables.

This is important data flow.

It is NOT simply:

    result = function();

It is more like:

    function(
        &datablock,
        &parameter
    );

Therefore information can flow:

    input
       |
       v
    helper
       |
       +----> modifies datablock
       |
       +----> modifies parameter
       |
       v
    status


----------------------------------------------------------------------
C. VERSION / MODE DETECTION
----------------------------------------------------------------------

The code then reads:

    datablock + 2

The 16-bit field at this location is transformed using byte
reversal.

This means the datablock contains an encoded field whose byte
ordering matters.

That field is then used to select between:

    Version 1
    Version 2
    Unsupported


----------------------------------------------------------------------
D. VALIDATION
----------------------------------------------------------------------

The version selection changes parameters used by the later
validation path.

Observed values:

    Version 1:
        validation_mode      = 0
        validation_parameter = 0x14

    Version 2:
        validation_mode      = 1
        validation_parameter = 0x20

So conceptually:

        datablock
            |
            v
       read version
            |
       +----+----+
       |         |
      V1        V2
       |         |
       v         v
     mode=0    mode=1
     size=20   size=32
       |         |
       +----+----+
            |
            v
       validation
            |
            v
          result


======================================================================
PART 7 - WHAT THE FIRST FUNCTION DOES TO A VALUE
======================================================================

The first function has a different role.

It takes:

    field_id
    value

The field ID is converted to:

    index = field_id - 0x6B

The valid range is six entries.

A lookup table chooses one of several transformations.

Conceptually:

                 field_id
                     |
                     v
              field_id - 0x6B
                     |
                     v
                 range check
                     |
             +-------+-------+
             |               |
          invalid           valid
             |               |
             v               v
           ERROR        lookup table
                             |
                             v
                       transformation
                             |
                             v
                     low-level operation
                             |
                             v
                         status


The transformations observed are:

    helper(value, 1)  << 14
    helper(value, 1)  << 15
    helper(value, 1)  << 1
    helper(value, 1)  << 2
    helper(value, 16) << 16
    helper(value, 1)

This looks like construction/placement of a field value into a
larger register or hardware-specific representation.

However, the exact meaning of the helper is unknown from the
provided function alone.


======================================================================

======================================================================

The first function and second function should not automatically
be treated as the same operation.

FIRST FUNCTION:

       |

    lookup
       |

    transform value
       |

       |

SECOND FUNCTION:

int write_encoded_field(int fieldId, int inputValue)
{
    /*
     * Convert the field identifier into a switch index.
     */
    int index = fieldId - 0x6B;


    /*
     * Only six field IDs are supported by this dispatch table.
     */
    if (index > 5)
    {
        /*
         * The original program reports:
         *
         *     Unsupported efuse field
         *
         * and returns -1.
         */
        report_error(
            "Unsupported efuse field"
        );

        return -1;
    }


    /*
     * Look up which operation is associated with this field.
     *
     * The real program uses an indirect branch through a byte
     * table. In normal C, we can understand this as a switch.
     */
    int operation = switchTable[index];


    /*
     * Perform the field-specific transformation.
     */
    switch (operation)
    {
        case SHIFT_14:
        {
            int transformed =
                helper_transform(inputValue, 1);

            transformed =
                transformed << 14;

            /*
             * Continue into the common hardware operation.
             */
            break;
        }


        case SHIFT_15:
        {
            int transformed =
                helper_transform(inputValue, 1);

            transformed =
                transformed << 15;

            break;
        }


        case SHIFT_1:
        {
            int transformed =
                helper_transform(inputValue, 1);

            transformed =
                transformed << 1;

            break;
        }


        case SHIFT_2:
        {
            int transformed =
                helper_transform(inputValue, 1);

            transformed =
                transformed << 2;

            break;
        }


        case SHIFT_16:
        {
            int transformed =
                helper_transform(inputValue, 16);

            transformed =
                transformed << 16;

            break;
        }


        case NO_SHIFT:
        {
            int transformed =
                helper_transform(inputValue, 1);

            break;
        }
    }


    /*
     * All supported operations eventually reach the same
     * low-level operation.
     */
    int status =
        low_level_operation(6);


    /*
     * Zero means the low-level operation did not report an error.
     */
    if (status == 0)
    {
        return 0;
    }


    /*
     * Non-zero status causes an error report.
     */
    report_error(
        "Writing MTK Spare C_CTRL0 fuse bank failed",
        status
    );

    return -1;
}


/*
 * ================================================================
 * DATABLOCK VERSION EXTRACTION
 * ================================================================
 */

int extract_version(void *datablock)
{
    /*
     * A NULL datablock cannot contain a version.
     */
    if (datablock == NULL)
    {
        return 0;
    }


    /*
     * Read a 16-bit field at byte offset +2.
     */
    uint16_t raw =
        read_u16((char *)datablock + 2);


    /*
     * The assembly performs byte reversal.
     *
     * This is related to the representation/endianness of the
     * encoded data.
     */
    uint32_t converted =
        byte_reverse_32(raw);


    /*
     * Extract the upper 16 bits.
     */
    return converted >> 16;
}


/*
 * ================================================================
 * DATABLOCK MODE
 * ================================================================
 */

int determine_datablock_mode(void *datablock)
{
    if (datablock == NULL)
    {
        return 0;
    }


    /*
     * Read the same +2 field.
     */
    uint16_t raw =
        read_u16((char *)datablock + 2);


    /*
     * Reconstruct the encoded representation.
     */
    uint32_t converted =
        byte_reverse_32(
            ((uint32_t)raw) << 16
        );


    /*
     * Compare against 2.
     *
     * The original conditional select returns:
     *
     *     40 if value < 2
     *     42 otherwise
     *
     * This exact behavior should be preserved in the
     * reconstruction.
     */
    if (converted < 2)
    {
        return 0x28;       /* 40 */
    }
    else
    {
        return 0x2A;       /* 42 */
    }
}


/*
 * ================================================================
 * MAIN VALIDATION / VERIFICATION LOGIC
 * ================================================================
 */

int validate_datablock(void *input)
{
    /*
     * This variable will eventually point to the datablock.
     */
    void *datablock = NULL;


    /*
     * Initial parameter supplied to the first helper.
     */
    uint32_t parameter = 0x20;


    /*
     * Ask the lower-level routine to obtain/process the data.
     *
     * The exact semantics of this helper are unknown.
     */
    int result =
        get_datablock(
            input,
            &datablock,
            &parameter
        );


    /*
     * IMPORTANT:
     *
     * The assembly uses:
     *
     *     TBZ w0, #0, ...
     *
     * Therefore only bit 0 is tested.
     */
    if ((result & 1) == 0)
    {
        /*
         * Bit 0 is clear.
         *
         * The function leaves the validation path.
         */
        return 0;
    }


    /*
     * Process/validate the datablock structure.
     *
     * The helper receives addresses, so it may update both
     * datablock and parameter.
     */
    int processStatus =
        process_datablock(
            &datablock,
            &parameter
        );


    /*
     * Only status 0xF is accepted for the next stage.
     */
    if (processStatus != 0xF)
    {
        return 0;
    }


    /*
     * The helper must have produced a valid datablock pointer.
     */
    if (datablock == NULL)
    {
        return 0;
    }


    /*
     * Read/interpet information from the datablock.
     */
    int version =
        extract_version(datablock);


    int mode =
        determine_datablock_mode(datablock);


    /*
     * The assembly explicitly masks the value to 16 bits.
     */
    mode &= 0xFFFF;


    /*
     * These parameters control the version-specific path.
     */
    int validationMode;
    int validationParameter;


    /*
     * ============================================================
     * VERSION 2
     * ============================================================
     */
    if (mode == 2)
    {
        /*
         * Original assembly:
         *
         *     w21 = 1
         *     w22 = 0x20
         */
        validationMode = 1;
        validationParameter = 0x20;


        /*
         * Diagnostic message in the binary proves that this
         * path is considered a Version 2 datablock.
         */
        log(
            "validate_hash_password: Version 2 datablock"
        );
    }


    /*
     * ============================================================
     * VERSION 1
     * ============================================================
     */
    else if (mode == 1)
    {
        /*
         * Original assembly:
         *
         *     w21 = 0
         *     w22 = 0x14
         */
        validationMode = 0;
        validationParameter = 0x14;


        log(
            "validate_hash_password: Version 1 datablock"
        );
    }


    /*
     * ============================================================
     * UNSUPPORTED
     * ============================================================
     */
    else
    {
        /*
         * The binary contains an explicit diagnostic for this
         * condition.
         */
        log(
            "validate_hash_password: Unsupported datablock"
        );

        return 0;
    }


    /*
     * ============================================================
     * VERSION-SPECIFIC VALIDATION
     * ============================================================
     *
     * The supplied disassembly does not include the implementation
     * of every helper called from here.
     *
     * Therefore we represent the remaining operation abstractly.
     *
     * The important data flow is:
     *
     *     datablock
     *         +
     *     validationMode
     *         +
     *     validationParameter
     *         |
     *         v
     *     validation helper
     *         |
     *         v
     *     result
     */

    int validationResult =
        validate_hash_or_password(
            datablock,
            validationMode,
            validationParameter
        );


    /*
     * The precise success/failure semantics depend on the body of
     * the omitted helper.
     */
    return validationResult;
}

PART 12 - WHAT WE CAN PROVE VS WHAT WE CANNOT YET PROVE
======================================================================

PROVABLE FROM THE SUPPLIED DISASSEMBLY:

1. There is a six-entry field dispatch range beginning at 0x6B.

2. A byte lookup table controls an indirect branch.

3. Several field-specific bit-shift operations exist.

4. The final common operation receives constant value 6.

5. A non-zero result from that final operation causes an error
   message concerning writing an MTK Spare C_CTRL0 fuse bank.

6. The validation function tests bit 0 of an earlier helper result.

7. A subsequent helper must return exactly 0xF for the main
   datablock path to continue.

8. A datablock pointer must be non-NULL.

9. The datablock contains a 16-bit field at offset +2.

10. That field is byte-order transformed.

11. The code distinguishes version/mode-specific paths.

12. The binary explicitly contains messages for:
       - Version 1 datablock
       - Version 2 datablock
       - Unsupported datablock

13. Version-specific parameters are:
       Version 1 -> 0 and 0x14
       Version 2 -> 1 and 0x20


NOT PROVABLE FROM THESE SNIPPETS ALONE:

1. The exact cryptographic algorithm.

2. The exact meaning of the input value.

3. The exact meaning of the +2 datablock field without examining
   the surrounding structure and callers.

4. Whether "password" means a literal user password, hash,
   credential, or another authentication object.

5. Whether a successful validation directly unlocks a device.

6. The exact meaning of FUN_ffff000050f90010.

7. The exact meaning of FUN_ffff000050f90f78.

8. The exact meaning of FUN_ffff000050f29978.

9. The exact meaning of FUN_ffff000050f9b6f0.

10. The exact mapping from the six switch-table entries to the
    six field IDs, because the actual bytes of the switch table
    were not supplied.

Think of the second function as a PIPELINE:

        input

    select Version 1 / Version 2
          |
          v
    choose validation parameters
          |
          v
    perform validation
          |
          v
    return status


Think of the first function as a DISPATCHER:

        field ID
           |
           v
      normalize ID
           |
           v
      range check
           |
           v
      lookup operation
           |
           v
      transform value
           |
           v
      common low-level operation
           |
           v
      success/error


The two pieces therefore represent different stages of logic.

The first is primarily:

        FIELD -> TRANSFORMATION -> LOW-LEVEL OPERATION

The second is primarily:

        DATABLOCK -> VERSION/MODE -> VALIDATION
